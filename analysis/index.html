빅데이터 분석 정의서

주제 : 굿닥 AI 병원 선택 어시스턴트

대상 기업 : 굿닥 | 팀 : 독수리5형제

2026. 09. 17.

Ⅰ. 개요

1. 아이디어 주제굿닥 앱 리뷰와 보건의료 공공데이터를 결합한 AI 병원 선택 어시스턴트
· 진단하는 AI가 아니라, '어느 병원에 갈지' 고르는 일을 돕는 AI다.
· 본 서비스는 병원 선택을 돕는 정보 제공 서비스이며 의학적 판단을 대신하지 않습니다.
2. 개발 목표몸이 불편한 이용자가 자기 상황(위치·시간·진료과)에 맞는 병원을 여러 앱을 오가지 않고 한 번에 고르게 한다.
· 근거: 리뷰 3,194건 LDA 분석에서 '병원 검색·정보' 토픽이 AI로 풀 수 있는 토픽 중 가장 크게 나타났다 (가장 큰 토픽 1 '예약'은 시스템 안정성 문제라 범위 밖).
3. 개발 내용① 자연어 조건 추출 — 문장에서 지역·시간·진료과·주차 조건을 뽑는다
② 공공데이터 검색 — 심평원 병원정보에서 조건에 맞는 곳을 좁힌다
③ 진료시간 판정 — 지금 문을 열었는지 판단하고, 모르면 '미확인'으로 표시한다
④ 증상 → 진료과 안내 — 애매하면 되묻는다
⑤ 약국·심야약국 찾기
⑥ 응급실 실시간 병상 조회
⑦ 음성 입력·목소리 안내 — 말로 묻고 귀로 듣는다
⑧ 길찾기 연결 — 네이버지도·카카오맵으로 넘긴다

Ⅱ. 기능별 빅데이터 분석 명세서

· 모든 수치는 실제 수집·분석 결과이며, 확인되지 않은 값은 '미확인'으로 표기한다.

기능 1. 고객 Pain Point 분석 (기획 근거 도출)

데이터 정의굿닥 안드로이드 앱 이용자 리뷰 전문, 별점, 작성일시, 앱 버전, 도움됨 수
· 개인정보(작성자명)는 저장하지 않는다.
데이터 획득 방법구글 플레이 스토어 리뷰 수집 (google-play-scraper 라이브러리)
· 패키지명 : com.ksncho.hospitalinfo
· 요청 간 1초 이상 간격, robots.txt 준수
· 수집량 : 4,311건 (2017-05 ~ 2026-08)
· 스크립트 : src/collect/play_reviews.py
수집 데이터review_id, score, content, at, thumbsUpCount, appVersion
예) score=1, content="최근 진료중 표시 누르면 인근 병원 표시가 안됩니다. 서울 또는 멀리있는 병원 위주입니다"
· 평균 별점 4.12점, 별 1~2점 837건
전처리 과정① 결측·중복 제거
② 자음·모음만 있는 글(ㅋㅋㅋ, ㅠㅠ) 제외 — 글자의 50% 초과 시
③ 10자 미만 단문 제외
④ kiwipiepy 형태소 분석 → 일반명사·고유명사만 추출
⑤ 불용어 제거 (굿닥, 앱, 그냥, 진짜 등)
⑥ 두 글자 미만 단어 제외
전처리 데이터분석 대상 3,194건 (원본 4,311건에서 자모·단문 제외)
예) "최근 진료중 표시 누르면..." → [진료, 표시, 인근, 병원, 서울]
데이터 분석 목표이용자가 어느 단계에서 막히는지를 찾고, 그중 AI로 풀 수 있는 구간을 가려낸다.
데이터 분석 시나리오1) TF-IDF (scikit-learn TfidfVectorizer)
- min_df=3, max_df=0.5 로 너무 드물거나 흔한 단어 제외
- 전체 리뷰와 부정 리뷰(별 1~2점)를 따로 계산해 비교
2) LDA 토픽 모델링 (scikit-learn LatentDirichletAllocation)
- n_components=6, learning_method='batch', max_iter=30
- random_state=42 로 고정해 같은 결과가 나오게 함
3) 토픽별 평균 별점을 구해 감성 방향을 판단
4) 고객 여정 단계에 매핑하고 'AI 해결 가능' 여부를 표시
· 스크립트 : src/analysis/topics.py, src/analysis/painpoint.py

[그림] 토픽별 리뷰 수와 평균 별점 (파란색 = 우리 서비스가 직접 푸는 문제)

모델 생성 및 학습■ 사용 모델 : LDA (Latent Dirichlet Allocation, 잠재 디리클레 할당)
· scikit-learn LatentDirichletAllocation
· 정답 라벨이 없는 비지도 학습이므로 학습용·시험용 데이터를 나누지 않는다
■ 입력 행렬 생성
· CountVectorizer(횟수 기반) — LDA 는 빈도 행렬이 정석이다
· min_df=3, max_df=0.5 — 너무 드물거나 너무 흔한 단어 제외
■ 학습 설정 (하이퍼파라미터)
· n_components=6 — 토픽 6개
· learning_method='batch' — 전체를 한 번에 학습
· max_iter=30 — 최대 반복 30회
· random_state=42 — 항상 같은 결과가 나오도록 고정
■ 학습 데이터 : 전처리를 마친 리뷰 3,194건
■ 토픽 수를 6으로 정한 근거
· 토픽 수를 바꿔 가며 대표 단어를 사람이 읽고, 의미가 서로 겹치지 않으면서 해석이 되는 지점을 6으로 판단했다
· 스크립트 : src/analysis/topics.py
검증■ 재현성 검증 — 통과
· random_state=42 로 고정하여, 다시 돌려도 토픽과 비율이 동일하게 나오는 것을 확인
■ 타당성 검증 (토픽별 평균 별점 대조) — 통과
· 긍정으로 해석한 토픽의 평균 별점이 높고(4.76·4.84), 불만으로 해석한 토픽이 낮게(3.28) 나와 해석 방향이 일치
· 별점은 학습에 쓰지 않은 값이므로 독립적인 대조 기준이 된다
■ 사람 검토 — 통과
· 토픽별 대표 리뷰 원문을 직접 읽고 대표 단어와 맞는지 확인
■ 한계 (밝혀 둔다)
· Perplexity·Coherence 같은 수치 지표는 산출하지 않았다
· 토픽 해석에는 사람의 판단이 들어가므로 절대적 기준이 아니다

기능 2. 자연어 조건 추출 및 병원 검색

데이터 정의전국 병원 기본정보(기관명·종별·주소·좌표·전화), 진료과목, 진료시간·주차 등 세부정보, 평가등급
데이터 획득 방법① 건강보험심사평가원 병원정보서비스 Open API (공공데이터포털)
- https://www.data.go.kr
- 주의: 광주는 전남과 통합되어 sidoCd=360000 으로 조회해야 한다
② 심평원 배포 파일 '전국 병의원 및 약국 현황' (자료번호 11925)
- https://opendata.hira.or.kr (공공누리 제1유형, 출처표시)
③ 국립중앙의료원 응급의료정보(E-Gen) — 진료시간 보강
· 확보량 : 병원 79,819곳, 진료과 매핑 77,107곳, 세부정보 76,934곳
수집 데이터ykiho(암호화요양기호), 기관명, 종별, 시도·시군구, 주소, XPos/YPos(경위도), 전문의 수(mdeptSdrCnt 등), 진료시간, 주차대수
예) 오치오케이정형외과의원 / 의원 / 전남광주통합특별시 북구 / 월~금 08:30~18:00 / 전문의 1명
전처리 과정① 시도·시군구 표기 통일 (전남광주통합특별시 → 광주 북구 등)
② 지역 별칭 사전 구축 — 같은 곳을 가리키는 표기를 한데 묶음
③ 진료과목 코드 → 이름 매핑
④ 진료시간을 요일별 구조로 변환, 없으면 null 유지
⑤ 심평원 세부정보와 E-Gen 진료시간을 기관번호로 병합 (중복 시 E-Gen 우선)
⑥ 서비스용 단일 묶음으로 압축 저장
전처리 데이터data/serve/bundle.json.gz (8.2MB)
· 진료시간 확보 59,378곳 (전체의 74.4%)
· 지역 표기 4,915가지 인식
· 나머지는 '진료시간 미확인'으로 두고 지어내지 않는다
데이터 분석 목표한 문장에서 지역·시간·진료과·주차 조건을 뽑아내고, 그 조건에 맞는 병원을 거리순으로 제시한다.
데이터 분석 시나리오1) 규칙 기반 조건 추출
- 지역 사전 최장일치 매칭 → 시도·시군구 확정
- 시간 표현('지금', '저녁 7시', '주말') → 요일·시각으로 변환
- 진료과 사전 매칭 (별칭 포함)
2) 동명 지역 처리 — '광주'처럼 여러 곳이면 되묻는다
3) 조건 필터링 후 하버사인 공식으로 거리 계산, 가까운 순 정렬
4) 진료시간을 현재 시각과 대조해 '진료중 / 휴진 / 미확인' 판정
· 스크립트 : src/chains/extract_conditions.py, src/chains/region_index.py, src/chains/pipeline.py
데이터 분석 결과· '광주 북구 정형외과 지금 문 연 곳' 입력 시 조건 3개를 모두 추출하고 후보를 거리순으로 제시함 (실행 확인)
· 진료시간이 공개되지 않은 병원은 건수를 함께 안내하여 전화 확인을 유도함
· 단위 테스트 172개 통과 (2026-09-16 재실행)
모델 생성 및 학습■ 학습하는 모델을 쓰지 않는다 — 규칙 기반(정규식 + 사전)으로 만들었다
■ 그렇게 정한 이유
· 문장과 정답 조건이 짝지어진 학습 데이터가 존재하지 않는다
· 틀렸을 때 어느 규칙 때문인지 추적해 바로 고칠 수 있어야 한다
· 병원 안내는 틀린 답을 그럴듯하게 내놓으면 안 되는 영역이다
■ 모델 대신 만든 것
· 지역 사전 : 시도·시군구·별칭 4,915가지 (최장일치 매칭)
· 진료과 사전 : 심평원 진료과목 분류 48종 + 별칭
· 시간 표현 규칙 : '지금'·'저녁 7시'·'주말' → 요일·시각 변환
· 거리 계산 : 하버사인(Haversine) 공식 — 학습이 아니라 수식이다
■ LangChain 은 대화 흐름 관리에만 쓰고, 병원 목록은 공공데이터에서만 가져온다 (생성형 모델이 병원을 지어내지 않는다)
검증■ 단위 테스트 172개 전부 통과 (2026-09-16 실행, 63.9초)
· tests/test_backtest.py 73개 — 전체 기능 백테스트
· tests/test_extract_conditions.py 11개 — 조건 추출
· tests/test_search_nationwide.py 9개 — 전국 검색
■ 검색 정확성 검증 항목 — 모두 통과
· 전국 어느 지역을 물어도 결과가 나오는가
· 거리 계산이 정확한가 (하버사인 결과 대조)
· 시간 조건이 결과 0건을 만들지 않는가
· 진료시간이 확인된 곳이 미확인보다 앞에 오는가
· 추천 이유가 항상 함께 나오는가
· '내과'를 찾을 때 한방병원이 먼저 나오지 않는가
■ 재현 방법 : python -m pytest tests/ -q

기능 3. 증상 → 진료과 안내

데이터 정의증상 표현과 진료과의 대응 관계
· 의학적 진단이 아니라 '어느 과로 가면 되는지' 안내에 한정한다
데이터 획득 방법심평원 진료과목 분류(48종)를 기준으로 삼고, 리뷰에 나타난 증상 표현을 수집해 대응표를 만든다.
· 근거 문서 : docs/증상별_진료과_매핑표.md
수집 데이터예) '목이 아파요' → 이비인후과 / 내과
'허리가 아파요' → 정형외과 / 신경외과
전처리 과정① 증상 표현 정규화 (띄어쓰기·어미 변형 흡수)
② 한 증상이 여러 과에 걸리는 경우를 그대로 유지
③ 응급 신호 표현은 별도 분리
전처리 데이터증상 → 진료과 대응 사전 (복수 대응 허용)
데이터 분석 목표증상 문장에서 갈 만한 진료과를 좁히되, 확신할 수 없으면 단정하지 않고 되묻는다.
데이터 분석 시나리오1) 증상 키워드 매칭
2) 대응 진료과가 2개 이상이면 선택지를 제시하고 되묻기
3) 응급 신호가 감지되면 119 안내를 먼저 표시
4) 어느 과인지 판단이 서지 않으면 '미확인'으로 두고 진료과 직접 선택을 안내
· 스크립트 : src/chains/dialog.py
데이터 분석 결과· 애매한 입력에 대해 단정하지 않고 되묻는 동작 확인
· '진단', '처방', '이 병일 가능성' 같은 의료 표현은 코드·UI·문서 어디에도 쓰지 않음
모델 생성 및 학습■ 학습 모델 없음 — 증상·진료과 대응 사전으로 처리한다
■ 그렇게 정한 이유
· 증상에서 병을 추론하는 모델은 의료 행위에 가까워진다
· 우리는 '어느 과로 가면 되는지'까지만 안내하도록 범위를 정했다
· 사전은 내용이 눈에 보이므로 틀린 대응을 바로 찾아 고칠 수 있다
■ 만든 것 : 증상 표현 → 진료과 대응표 (한 증상에 복수 진료과 허용)
· 근거 문서 : docs/증상별_진료과_매핑표.md
· 스크립트 : src/chains/dialog.py
검증■ 단위 테스트 — 통과 (tests/test_voice_symptom.py 7개)
· 증상을 진료과로 바꾸는가
· 애매한 입력에 단정하지 않고 되묻는가
■ 의료 안전 검증 — 통과 (백테스트 '의료 안전' 항목)
· 진단·병명을 말하지 않는지 자동으로 검사한다
· 진단을 유도하는 문장을 넣어도 병명이 출력되지 않음을 확인
■ 한계 (밝혀 둔다)
· 대응표에 없는 표현은 '미확인'으로 두고 진료과 직접 선택을 안내한다
· 대응표의 의학적 타당성은 전문가 감수를 받지 않았다

기능 4. 약국·심야약국 및 응급실 실시간 병상

데이터 정의약국 기본정보와 운영시간, 응급의료기관의 실시간 가용 병상
데이터 획득 방법① 심평원 약국정보서비스 — 약국 기본정보
② 국립중앙의료원 응급의료정보(E-Gen) Open API
- 약국 운영시간, 응급실 실시간 병상·장비
· 확보량 : 약국 25,757곳, 운영시간 17,643곳
수집 데이터약국명, 주소, 전화, 좌표, 요일별 운영시간
응급실 가용 병상 수, 입원실·수술실·중환자실, CT·MRI·인공호흡기, 정보 갱신 시각
전처리 과정① 심평원 약국과 E-Gen 운영시간을 기관번호로 병합
② 야간(22시 이후)·심야(24시 이후)·24시간 구분 플래그 생성
③ 운영시간 미공개 약국은 목록에서 제외하고 그 수를 안내에 표시
④ 응급실 병상은 저장하지 않고 조회 시점에 받아 온다
전처리 데이터약국 운영시간 17,643곳 (전체 25,757곳 중)
응급실 정보는 갱신 시각과 함께 표시
데이터 분석 목표지금 문을 연 약국과, 지금 갈 수 있는 응급실을 알려준다.
데이터 분석 시나리오1) 현재 시각·요일과 운영시간 대조
2) '야간', '심야', '24시간', '일요일' 조건별 필터
3) 응급실은 조회 시각을 함께 표시하고 119 안내를 먼저 띄운다
4) 조건에 맞는 곳이 없으면 가까운 순으로 보여주되 '조건에 맞는 곳을 찾지 못했다'를 먼저 알린다
· 스크립트 : src/chains/emergency.py, src/collect/egen_api.py
데이터 분석 결과· 실시간 병상 조회 동작 확인 (갱신 시각 함께 표시)
· 운영시간 미확인 약국 수를 함께 안내하여 오해를 막음
모델 생성 및 학습■ 학습 모델 없음 — 시각 대조 규칙과 실시간 조회로 처리한다

· 야간(22시 이후)·심야(24시 이후)·24시간 구분 규칙

기능 5. 음성 입력·목소리 안내

데이터 정의이용자의 음성(입력)과 안내 문장(출력)
· 음성은 저장하지 않는다. 글자로 바뀐 즉시 버린다.
데이터 획득 방법브라우저 내장 Web Speech API (별도 수집·저장 없음)
· 2026-09-15 확인 : 크롬 152에서 ko-KR 인식과 한국어 음성 2종 동작
· 외부 음성 서비스를 쓰지 않아 키·요금·서버가 필요 없다
수집 데이터없음. 인식된 문장은 기존 조건 추출 로직으로 그대로 전달된다.
전처리 과정① 중간 인식 결과를 화면에 실시간 표시 (이용자 확인용)
② 최종 문장만 검색 로직에 전달
③ 출력 시 시각 표기를 사람 말로 변환
- '08:30~17:00' → '오전 8시 30분부터 오후 5시까지'
④ 끝 시각이 시작보다 이른 자료는 '다음 날'을 붙여 읽는다 (숫자는 고치지 않는다)
전처리 데이터예) 음성 '광주 북구 정형외과 지금 문 연 곳'
→ 텍스트 동일 → 조건 {지역:광주 북구, 진료과:정형외과, 시간:지금}
데이터 분석 목표손으로 글자를 치기 어려운 상황(급함·고령)에서도 같은 검색을 쓸 수 있게 한다.
데이터 분석 시나리오1) 음성 → 텍스트 (브라우저 내장 인식기, ko-KR)
2) 이후 처리는 기능 2와 완전히 동일 (로직을 새로 만들지 않음)
3) 결과를 문장으로 재구성해 음성으로 출력
4) 마이크가 없는 기기는 그 사실을 그대로 안내
· 스크립트 : src/api/static/widget.js
데이터 분석 결과· 읽어주는 문장 생성 확인 (병원·약국·응급실·되묻기 4종)
· 화면에만 있던 경고 문구도 음성에 포함되도록 수정
· 실제 발화 인식은 마이크가 있는 기기에서 확인 필요
모델 생성 및 학습■ 학습 모델 없음 — 브라우저에 내장된 인식기를 그대로 쓴다
■ 그렇게 정한 이유
· 음성 인식 모델을 직접 학습시키려면 목소리를 모아야 하는데, 음성은 개인정보라 수집하지 않기로 했다
· 브라우저 내장 기능은 키·요금·서버가 필요 없다
■ 만든 것 : 읽어주기 문장 생성 규칙
· '08:30~17:00' → '오전 8시 30분부터 오후 5시까지'
· 끝 시각이 시작보다 이르면 '다음 날'을 붙인다 (숫자는 고치지 않는다)
· 스크립트 : src/api/static/widget.js
검증■ 단위 테스트 — 통과 (tests/test_voice_symptom.py)
· 읽어주는 문장이 4종(병원·약국·응급실·되묻기) 모두 생성되는가
· 시각 표기가 사람이 듣는 말로 바뀌는가
■ 브라우저 확인 — 통과 (2026-09-15, 크롬 152)
· ko-KR 인식 동작, 한국어 음성 2종 확인
■ 한계 (밝혀 둔다)
· 실제 발화 인식률은 측정하지 않았다. 마이크가 있는 기기에서 추가 확인이 필요하다
· 마이크가 없는 기기는 그 사실을 그대로 안내한다
